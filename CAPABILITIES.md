# Runtime capability observations

Baseline: upstream DSH interface range `>=0.2.1-rc.2 <0.2.2-0` (`engines.dsh`), verified on the released `0.2.1-rc.2` and `0.2.1-rc.3` lines. No exact DSH revision is required. Plugin 0.5.0 ships an optional native Agent Preset mode (a committed mirror of the DSH Standard preset composition plus the `thaliris-agent` row), first-run runtime provisioning, and native DSH tool grants per seeded role.

| Surface | Verified behavior | Limit |
|---|---|---|
| Core | Native subprocess imports neutral core/authority only; external anchor owns intent | Shared OS governance, not actor authentication |
| Root continuation | Native Workspace + persisted root Session/new Agent resumes exact anchor | Missing/changed native workspace anchor fails closed |
| Policy | Native Settings live forms, stored edits, revision conflicts; editable prompt and legal empty role list; `pythonExecutable` / `corePath` / `authorityDirectory` are optional volatile fields with a live manual override (`applies: 'live'`), and their names/positions plus the `policy` shape are unchanged from 0.4.x | The host row still fails closed without a usable runtime: unconfigured use returns `THALIRIS_NOT_CONFIGURED` / `THALIRIS_RUNTIME_NOT_READY` in the tool error and setup status, never at activation |
| Models | Native exact route metadata and configured allowed-set membership | No route ranking or online catalog smoke |
| Children | Fresh native spawn through `subagents.startActivation` with a reserved child id (caller delivery, `maxDepth: 1`), bounded handoff, role persona and exact tool allowlist/deny list installed on the child scope at `agent/created` before its first prompt, plus body checks, immediate ID/correlation recording; each dispatch registers a per-dispatch Agent Preset as the child's independent selection, so DSH refuses any later continuation once that dispatch ends or the adapter unloads | Current supported provider is local in-process spawn. The per-dispatch preset comprises no plugins; the child joins the parent's composition for its run |
| Roles | Six editable seeds (Investigator, Implementer, Focused Implementer, Reviewer, Curator, Reasoning Specialist); dispatch snapshots the selected role, recorded as `role_sha256`; seeds now ship curated native DSH tool grants (see Native role grants) | Roles are adjusted by user Settings edits; no Controller role registration. Non-writing roles rely on tool grants, not a native readonly classification |
| Model per dispatch | Controller-chosen route and reasoning effort within the role's allowed routes (isolation and division of labor first, then the cheapest allowed route and lowest effort that fit the working set; no cheap route in policy is respected), checked against native model reasoning efforts and recorded with the reservation | Actual model execution is what DSH ran; not separately observed by the adapter |
| Evidence continuity | Controller register/judge/status; dispatch-registered handoff; child `thaliris_observe` bound to the exact bound child and handoff; the compact open-evidence summary (totals plus bounded items, paged) returned with the child result and with register/judge/context results | No automatic relevance or acceptance; observation without an association is returned in FINAL |
| Controller overhead (Core 0.5.1) | `thaliris_task_status` is compact by default (`view: "full"`, `since_revision` optional); `thaliris_task_judge` takes one `judgment` or an atomic ordered `judgments` batch (one revision); write results carry the new revision and the evidence summary; the dynamic-context summary is not echoed in tool results; revision conflicts keep the text `TASK_ID_OR_REVISION_CONFLICT` and add Core's `code`, `recovery` and `details.changes_since` (task-id and revision mismatch distinguished); other Core `code`/`details` errors surface the same way | Strict CAS is unchanged: nothing is rebased or merged, and `changes_since` is a bounded non-exact review hint. Native tool execution of the new fields is not covered by the local checks |
| Project identity | Core 0.5.0 `.project-identity/` read (status, get, trace) and Controller-only amend, challenge and relate (plus, Core 0.5.2, Controller-only `thaliris_task_identity_note` and `thaliris_task_identity_suggest` with no ACTIVE task needed, a session scope keyed by the native Controller id, and an `identity_offer` line on a successful close only when Core returns one) through the bridge under the authority check and task-revision CAS; actor from the native Controller identity; one summary line in the dynamic task context only when an identity exists | No path-level child write guard exists in this adapter: a child's change to `.project-identity/` is detected afterwards (Core `UNRECORDED_CHANGE` or `INVALID`, Git diff), not prevented. Relations are registered ones only; Core records a human decision the Controller asserts and cannot authenticate a human. Native tool execution of the identity tools is not covered by the local checks |
| Task context | Controller records/milestone via Core `task_update`; bounded summary as native dynamic context, re-projected after compaction and restored after restart from this root's anchored ACTIVE tasks; the first prompt assembly after a restart awaits restoration | A failed or timed-out restoration leaves the context empty; history, not fresh verification |
| Dispatch history | Each finished dispatch is one append-only `dsh-dispatch` Core record (producer `dsh:adapter`); Active Work/Pending Results keep only current routing state; legacy history in Pending Results migrates on the next adapter write; tested beyond 50 dispatches | Core's 512-record/512 KiB task bounds still apply: past them a release or close succeeds but returns the archive text as `unrecorded` |
| Execution mode | Core `switch_mode` with human instruction, authority-digest and revision CAS; refused with active work | Instruction text is Controller-asserted, not human authentication |
| Recovery | Native catalog correlation + durable terminal Session reason; reservation archived as a `dsh-dispatch` record; completed/aborted tested | Unbound/cross-process liveness remains UNKNOWN; no uncertainty auto-release |
| Memory | Optional independent capability/provider packages; async external injection, bounded read/search/write and user grants | No embeddings/vector/RAG/credential management |
| Memory writes | Disabled default, manual/review Core proposals (pending until approved), human Remote approval recorded as a `dsh-memory-approval` record, explicitly opted-in auto | Approval is human-client governance within native Host trust |
| Uninstall | Native effects dispose provider/capability and the registered preset; routing and close continue | Sessions that recorded preset id `thaliris` become unresumable while the plugin is disabled/removed (`agent-preset/not-found`) and recover after re-enable + restart |
| Lifecycle (install / upgrade / disable / re-enable / remove) | Profile `cordis.patch.yml` rows, installed package, roles/routes/workspace bindings and task state survive native package operations; row ids `thaliris`/`thaliris-api`, namespace `thaliris` and preset id `thaliris` are stable; toggles only change the bundle list/`disabled` state and never rewrite user config | Package changes are host-process changes: restart DSH to make them effective (the native manager reports `restart-required`, possibly `unmanaged-plugin` because the preset is registered at runtime); live Desktop maintenance needs separate human authority |
| Install | Normal native bundle install from `github:Iris0fTheValley/Thaliris-dsh` through the Desktop/Web Plugins page, a Creator-mode `plugin_manager` call, or `dsh plugin --profile <p> add …`; the package declares `dsh.bundle.patch` + `dsh.client` + `./preset`, ships its prebuilt client and has no install hooks | Native `plugin_manager` is available only in Creator mode (a normal Standard session has no install tool); the npm-installed CLI refuses the Desktop profile; package changes apply after a DSH restart; the default branch is still the incompatible 0.3.3 line until 0.5.0 is published there |
| Agent Preset mode | The global host row registers the persistent preset `{ id: 'thaliris', name: 'Thaliris', order: 10 }` programmatically when `agentPresets` exists; its composition mirrors the 22 top-level DSH Standard preset rows plus `{ id: 'thaliris-agent', name: '@thaliris/dsh-plugin/preset' }`; roster lists it under Custom and the default stays `standard` | No per-preset icon; custom names are not localized by the host; the mode exists only on Web/Desktop profiles that compose the Agent Preset registry (headless has none) |
| Mode isolation | Model-visible surface (tools, Controller prompt, dynamic task context, child composition and dispatch) lives in the `./preset` child and is scope-layered, so an unselected/Standard session receives none of it | Preset child `apply` bodies mount eagerly for every declared preset: the preset child is side-effect-free at `apply` and gates all behavior inside scoped registrations |
| Default mode | Native Settings → Agent presets → "Set as new task default" writes `agent-preset-registry.selectedDefault`; only new sessions resolve it; the plugin never writes it automatically | A saved default pointing at a disabled/removed preset is not self-healed by DSH (`agent-preset/not-found`) — reset to `standard` before disabling/removing |
| First-run provisioning | Lazy, on the first Thaliris tool call or an explicit human Gateway action; detects host-bundled CPython (then PATH, ≥ 3.11), creates a `--without-pip` venv under the authority directory, fetches the pinned Core tarball with Node `fetch`, verifies archive + package-tree SHA-256, installs by pure source copy, verifies import/version/state schema, writes atomic `runtime.json`; cold ≈ 1.6 s measured, idempotent after; single-flight with a cross-process lock | Provisioning needs network (or a staged `THALIRIS_CORE_TARBALL`) and a writable authority directory outside the workspace; failure leaves the plugin loaded with a code + recovery; `runtime.json` is unsigned (per-process import probe is the readiness gate) |
| Workspace auto-bind | When `policy.workspaces` is empty and the current native workspace's persistent root session is Thaliris-selected, the host row persists one enabled `{workspaceId, root}` binding through the native profile editor and reports it (`setupStatus().workspaceAutoBind`, host log); a non-empty list is never appended to and unselected sessions never bind | The write stores the complete composed raw config (native ConfigEditor semantics); preset-selection detection is cached per preset id; workspace re-registration changes the native id, breaking old task association |
| Native role grants | Seeded role templates carry curated native DSH tool grants per capability (investigator; implementer/focused-implementer; reviewer/reasoning-specialist read-only; curator); dispatch intersects stored names with the dispatching agent's visible catalog, logs unsupported names, and never rewrites stored user roles; the settings page lists enabled roles with empty grants and applies the shipped recommendation only on an explicit click | Unknown tool names are filtered rather than errors; `tools: []` is still legal (only an evidence-associated dispatch then gets `thaliris_observe`); Controller/management tools are never role grants; recommendations exist only for shipped template ids |
| Settings page (0.5.0) | General tab: first-run setup state/verified/pin/progress/error with explicit Prepare/Re-check/Refresh and volatile path overrides saved with policy; Agent Preset health plus new-Session default with explicit Set/Restore native writes (native revision-fenced `selectedDefault`); recommended native permissions listed and applied only on click; Context tab shows the host-reported auto-bind marker and an explicit most-recent-Workspace bind; typed zh/en copy; page renders while the preset is unselected | The shared page has no public current-session/workspace read, so "bind most recent" is a snapshot composition; the auto-bind marker is process-local; setup actions have no Cancel control; recommendations exist only for shipped template ids; interactive rendering is jsdom/packed-smoke tested, not a live browser/Desktop click-through |
| Remote | Native Gateway SRC dispatch of templates, diagnostics, approval, and the human-only setup surface (`setupStatus`, `prepareRuntime`, `recheckRuntime`); temporary Web preview rendered the client and injected its API namespace | Setup methods are never model tools and take no caller IDs; extracted-package verification does not launch a browser; the original source repository's live Web integration was separately verified against Core source revision `256f760` |

Tests use real native source components and a scripted LLM. They do not establish Codex managed enforcement, universal process authentication, or semantic task completion authority. Verification bounds: the repo suites (`prompt-contract`, `composition-drift`, native composition, shared client 20/20 including the 0.5.0 setup/mode/recommendation cases, packed install smoke from the 38-file 0.5.0 archive) and the 66 pytest bridge/Core checks pass locally; settings-page interactions are exercised with the real client module stack in jsdom, not in a live browser/Desktop UI; 0.5.0 installs and activates in isolated 0.2.1-rc.3 Web and headless hosts using separate `DSH_HOME` directories, with the preset roster visible and the default still `standard`. Live Desktop activation (install into the running Desktop profile, restart, observe) is **not** verified by this repository and needs the user's own restart; rc.2 is covered by the CI tag matrix (composition drift gate), not by a local real host.
