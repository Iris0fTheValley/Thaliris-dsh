# Core dependency provenance

The standalone DSH adapter consumes the host-neutral Python distribution `thaliris==0.5.2` from the Thaliris Core source pin [`fc170edddbc41ce09aba57d3cf30d9a50344c570`](https://github.com/Iris0fTheValley/Thaliris/tree/fc170edddbc41ce09aba57d3cf30d9a50344c570). The machine-readable pin is [`core.lock.json`](core.lock.json) (repository, commit, version and task state schema 7); CI checks out Core at exactly that commit, and `tests/test_core_lock.py` keeps the lock, this file and the tested Core source in agreement. The adapter does not vendor Core: `corePath` names an externally installed Core import root.

This pin (state schema stays 7; persisted state remains valid for Core 0.5.0 and 0.5.1) adds Core 0.5.2 natural identity formation, which the bridge (protocol 1, DSH plugin 0.3.2 and later) now uses through `thaliris.identity_basis`: Controller-only basis notes of the user's verbatim long-term statements (`identity_note`, `identity_note_list`), suggestion preferences at session, workspace, project and global scope (`identity_suggest`), the `basis` and `suggestions` fields of `identity_status` (the bridge passes the native Controller id as the session key), and the once-per-new-note `identity_offer` line attached to a successful close result. All of it is stored machine-locally under `THALIRIS_HOME` (default home-directory store), outside the repository; the identity chain, `identity_summary` and the task ledger are unchanged. The 0.5.1 Controller-overhead surface stays: structured errors (`ThalirisError` with `code`, `recovery`, `details`, surfaced additively in the bridge failure envelope and the tool error, with the historical `TASK_ID_OR_REVISION_CONFLICT` text kept first), `core.revision_conflict` details (`changes_since`, a bounded non-exact review hint; strict CAS is unchanged and nothing is rebased or merged), atomic ordered judgment batches (`thaliris_task_judge` `judgments`), the compact evidence summary (`evidence_summary`, `task_write_response`) in register, judge, context and workstream-finish results, and the compact status packet (`task_status_packet` with `view` and `since_revision`; `thaliris_task_status` defaults to compact). It also keeps explicit Task-ID selection and task-scoped state and AuthorityStore paths (state schema stays 7). Relative to `thaliris==0.5.0` (`eb540d0c`) the Project Identity plane is unchanged. Relative to the earlier pin (`thaliris==0.4.6`, `b258d76`, same state schema 7) it adds the Project Identity plane (`thaliris.identity`): a repository-tracked, versioned `.project-identity/` baseline changed only by explicit amendments, with challenges and typed purpose relations, read through `identity_status`, `identity_get` and `identity_trace` and written through `identity_amend`, `identity_challenge` and `identity_relate` under the task-revision CAS. The bridge (protocol 1, operations added while both sides ship together) uses only those Core functions and the one-line `identity_summary`; it adds no second ledger and does not reuse the Memory Provider. Earlier in this lineage, relative to `thaliris==0.4.4` (`56e48ac`), Core added requirement-linked evidence continuity and explicit non-Git project lifecycle, which the bridge still uses through the continuity append contract, `task_update`, `task_status` and `AuthorityStore.switch_mode`.

Verified against this pin locally on Windows with Python 3.13 and Node.js, using the local Core checkout of the locked commit `fc170ed`: `tests/test_core_lock.py`, the bridge suites including the new `tests/test_bridge_identity_formation.py` (notes without a task, retraction, argument bounds, suggestion scopes and session-key keying, the close-time `identity_offer` once per new note and absent when off or when no note exists) with `tests/conftest.py` isolating `THALIRIS_HOME`, and `node tests/prompt-contract.mjs`. NOT run for this pin: the native composition (`test:native`), shared-client (`test:client`) and packed install-smoke (`test:install`) checks, which need a DSH source checkout, pnpm and the DSH host addon, and CI, which checks out Core at this commit and so needs it published (Core `feat/identity-formation` is not pushed). Previous pin evidence (`e29c837`, Core 0.5.1): Verified against this pin locally on Windows with Python 3.11 and Node.js 24, using the local Core checkout of the locked commit `e29c837` (66 passed, 237 s: the 51 existing tests plus 15 new ones): `tests/test_core_lock.py`, `tests/test_bridge.py`, `tests/test_bridge_continuity.py`, `tests/test_bridge_history.py`, `tests/test_bridge_identity.py` and the new `tests/test_bridge_ergonomics.py` (batch judgment atomicity and validation, structured conflict details and the single retry, task-id versus revision mismatch, compact versus full status, `since_revision`, write results carrying the revision and the evidence summary, open evidence paged rather than dropped). The identity checks cover (status, get, trace, amend, challenge, relate, CAS conflict, unknown-task and mismatched-controller refusal, absent identity unchanged, dynamic task context line only when an identity exists), plus `node tests/prompt-contract.mjs`. NOT run for this pin (`tests/native-loop.ts` was updated for the compact status and judge result shape but not executed): the native composition (`test:native`), shared-client (`test:client`) and packed install-smoke (`test:install`) checks, which need a DSH source checkout, pnpm and the DSH host addon, and CI, which checks out Core at this commit and so needs it published. The DSH native API is admitted by interface, not by revision: DSH plugin 0.4.1 declares `engines.dsh` `>=0.2.1-rc.2 <0.2.2-0`, and every build/test gate derives the checked-out host's version from its root `package.json` instead of requiring one commit. The service surface this plugin uses (Agent Presets, `subagents.startActivation` with `agentPreset`, `agent/created`, the `agent-preset/selected` session record, and the agent/tool/session services) is the same on the released `0.2.1-rc.2` and `0.2.1-rc.3` lines; `@deepseek-ai/cordis` 4.0.5, `@deepseek-ai/schemastery` 3.18.5 and Node.js `>=24.9` remain the library baseline. DSH plugin 0.3.2 remains the release for the previous baseline `5badb15009ae1756c3afe0ae0cef1faafc290ccc` (tag `dsh-v0.2.1-alpha.1`; before it `639ed01`, tag `dsh-v0.2.0-rc.2`). The 0.4.x migration follows the upstream subagent activation and preset-composition refactor: a dispatch reserves the child identity and starts it with `ctx.subagents.startActivation` (caller delivery, `maxDepth: 1`); the role persona and the exact tool grant, no longer accepted per request, are installed on the reserved child's own scope by an `agent/created` listener before its first prompt assembly (the same `deployment:persona-prefix` section and `tools.restrict` filter DSH formerly applied), and re-creating a Thaliris child outside its dispatch is refused: each dispatch registers a per-dispatch preset as the child's independent selection, so DSH refuses to continue the child once that preset is unregistered at dispatch end or adapter unload. Evidence for this range: on Windows with Node.js 24.14 and Python 3.11, `test:native` (`native-loop.ts`, `product-runtime.ts`) passes against released `0.2.1-rc.2` (`687f282`) and `0.2.1-rc.3` (`1f81c04`) checkouts and against the previously pinned master `22ddee3` (packages `0.2.1-rc.3`), and `test:client` passes against the rc.2 checkout; the native run used a locally installed Core 0.5.3 while the locked Core source baseline remains `fc170ed`. CI runs the native composition once per verified release tag (`dsh-v0.2.1-rc.2`, `dsh-v0.2.1-rc.3`) and admits any checkout whose root version is inside `engines.dsh`; CI evidence is recorded on the pull request. The packed install smoke (`test:install`) was not re-run for 0.4.1. The adapter keeps the authority and task ledger in Core; this repository ships no Core or Codex adapter source.

Historical evidence, not evidence for the current pin: the `0.4.6`/`b258d76` pin passed the bridge suites, the native composition, shared-client and prompt-contract checks and the packed activation smoke on Windows with Python 3.11 (Core installed as a wheel from a `git archive` of that commit into an isolated environment, local `npm pack` archives installed through the native Plugin Manager), and the `0.4.4`/`56e48ac` pin passed 18 bridge tests, the native checks and a packed activation smoke built from a local wheel. Earlier extracted-repository validation used a `thaliris-0.4.3-py3-none-any.whl` built from Core commit `7f4d9acf2e642e7b3c987d4ee45ebc6589d7cc15` (SHA-256 `c916e219c99bc52021c8d91d71ec93a5c1a1950eaa4ed71dec90be73658dec16`), which predates the Task-ID API. The original source repository's live Web integration was verified separately against Core source revision `256f760`, including a real active task, a fifth child, denial of native root tools to that child, and an explicit `DONE` close; a Desktop binary was not launched.
