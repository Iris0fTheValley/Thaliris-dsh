# Core dependency provenance

The standalone DSH adapter consumes the host-neutral Python distribution `thaliris==0.5.0` from the Thaliris Core source pin [`eb540d0c7f900449609544d107b4b308234c96f9`](https://github.com/Iris0fTheValley/Thaliris/tree/eb540d0c7f900449609544d107b4b308234c96f9). The machine-readable pin is [`core.lock.json`](core.lock.json) (repository, commit, version and task state schema 7); CI checks out Core at exactly that commit, and `tests/test_core_lock.py` keeps the lock, this file and the tested Core source in agreement. The adapter does not vendor Core: `corePath` names an externally installed Core import root.

This pin keeps explicit Task-ID selection and task-scoped state and AuthorityStore paths (state schema stays 7). Relative to the previous pin (`thaliris==0.4.6`, `b258d76`, same state schema 7) it adds the Project Identity plane (`thaliris.identity`): a repository-tracked, versioned `.project-identity/` baseline changed only by explicit amendments, with challenges and typed purpose relations, read through `identity_status`, `identity_get` and `identity_trace` and written through `identity_amend`, `identity_challenge` and `identity_relate` under the task-revision CAS. The bridge (protocol 1, operations added while both sides ship together) uses only those Core functions and the one-line `identity_summary`; it adds no second ledger and does not reuse the Memory Provider. Earlier in this lineage, relative to `thaliris==0.4.4` (`56e48ac`), Core added requirement-linked evidence continuity and explicit non-Git project lifecycle, which the bridge still uses through the continuity append contract, `task_update`, `task_status` and `AuthorityStore.switch_mode`.

Verified against this pin locally on Windows with Python 3.11 and Node.js 24, using the local Core checkout of the locked commit `eb540d0c` (the 51 tests below passed there: 51 passed, 232 s): `tests/test_core_lock.py`, `tests/test_bridge.py`, `tests/test_bridge_continuity.py`, `tests/test_bridge_history.py` and the new `tests/test_bridge_identity.py` (status, get, trace, amend, challenge, relate, CAS conflict, unknown-task and mismatched-controller refusal, absent identity unchanged, dynamic task context line only when an identity exists), plus `node tests/prompt-contract.mjs`. NOT run for this pin: the native composition (`test:native`), shared-client (`test:client`) and packed install-smoke (`test:install`) checks, which need a pinned DSH source checkout, pnpm and the DSH host addon, and CI, which checks out Core at this commit and so needs it published. The DSH source revision [`639ed015397290b3745d163aafe02ffee4aa3f84`](https://github.com/deepseek-ai/deepseek-harness/tree/639ed015397290b3745d163aafe02ffee4aa3f84) (tag `dsh-v0.2.0-rc.2`) remains the DSH native API baseline. The adapter keeps the authority and task ledger in Core; this repository ships no Core or Codex adapter source.

Historical evidence, not evidence for the current pin: the `0.4.6`/`b258d76` pin passed the bridge suites, the native composition, shared-client and prompt-contract checks and the packed activation smoke on Windows with Python 3.11 (Core installed as a wheel from a `git archive` of that commit into an isolated environment, local `npm pack` archives installed through the native Plugin Manager), and the `0.4.4`/`56e48ac` pin passed 18 bridge tests, the native checks and a packed activation smoke built from a local wheel. Earlier extracted-repository validation used a `thaliris-0.4.3-py3-none-any.whl` built from Core commit `7f4d9acf2e642e7b3c987d4ee45ebc6589d7cc15` (SHA-256 `c916e219c99bc52021c8d91d71ec93a5c1a1950eaa4ed71dec90be73658dec16`), which predates the Task-ID API. The original source repository's live Web integration was verified separately against Core source revision `256f760`, including a real active task, a fifth child, denial of native root tools to that child, and an explicit `DONE` close; a Desktop binary was not launched.
