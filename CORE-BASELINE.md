# Core dependency provenance

The standalone DSH adapter consumes the host-neutral Python distribution `thaliris==0.4.6` from the Thaliris Core source pin [`b258d762ae2838385f74b2dc63f9ac23457690ac`](https://github.com/Iris0fTheValley/Thaliris/tree/b258d762ae2838385f74b2dc63f9ac23457690ac). The machine-readable pin is [`core.lock.json`](core.lock.json) (repository, commit, version and task state schema 7); CI checks out Core at exactly that commit, and `tests/test_core_lock.py` keeps the lock, this file and the tested Core source in agreement. The adapter does not vendor Core: `corePath` names an externally installed Core import root.

This pin keeps explicit Task-ID selection and task-scoped state and AuthorityStore paths. Every new Task ID has an independent ledger under `.context/tasks/<UUID>/state.json`; a legacy singleton is retained as its own record and is never reused for a new task. DSH selects a task explicitly for each bridge operation; selection is process-local navigation and does not grant authority. Relative to the previous pin (`thaliris==0.4.4`, `56e48ac`, same state schema 7) the pin adds requirement-linked evidence continuity (requirements, handoffs, observations and model-authored judgments with unincorporated/unresolved status) and explicit non-Git project lifecycle. The bridge uses Core's continuity append contract, `task_update`, `task_status` and `AuthorityStore.switch_mode`; it adds no second ledger.

Verified against this pin on Windows with Python 3.11: the bridge suites (`tests/test_bridge.py`, `tests/test_bridge_continuity.py`, `tests/test_core_lock.py`) and the native composition, shared-client and prompt-contract checks with DSH source revision [`639ed015397290b3745d163aafe02ffee4aa3f84`](https://github.com/deepseek-ai/deepseek-harness/tree/639ed015397290b3745d163aafe02ffee4aa3f84) (tag `dsh-v0.2.0-rc.2`), which remains the DSH native API baseline. The packed activation smoke also passed: Core installed as a wheel from a `git archive` of the locked commit into an isolated Python 3.11 environment, and local `npm pack` archives installed through the native Plugin Manager. CI repeats these checks on Linux (`.github/workflows/ci.yml`) and the bridge suites on Linux and Windows with Python 3.11–3.13; no PyPI wheel or publication is claimed. The adapter keeps the authority and task ledger in Core; this repository ships no Core or Codex adapter source.

Historical evidence, not evidence for the current pin: the `0.4.4`/`56e48ac` pin passed 18 bridge tests, the native checks and a packed activation smoke built from a local wheel in an isolated Python 3.11 environment. Earlier extracted-repository validation used a `thaliris-0.4.3-py3-none-any.whl` built from Core commit `7f4d9acf2e642e7b3c987d4ee45ebc6589d7cc15` (SHA-256 `c916e219c99bc52021c8d91d71ec93a5c1a1950eaa4ed71dec90be73658dec16`), which predates the Task-ID API. The original source repository's live Web integration was verified separately against Core source revision `256f760`, including a real active task, a fifth child, denial of native root tools to that child, and an explicit `DONE` close; a Desktop binary was not launched.
