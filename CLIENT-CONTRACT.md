# Shared client contract

The shared Web/Desktop client is the `@thaliris/dsh-plugin/client` entry. It uses one native Plugins-page item, ConfigForms, native model and tool catalogs, native Workspace and Session projections, and the native Plugin Manager. A client view is a projection; it cannot replace records in the separately installed [Thaliris Core](https://github.com/Iris0fTheValley/Thaliris) or DSH, or imply completion.

## Native configuration

Initial prompt ownership and semantic endpoints are documented in
[PROMPT-CONTRACT.md](PROMPT-CONTRACT.md). Controller guidance is the editable
`policy.mjs` template; role seeds come from `role-templates.mjs` and the bundle
generator. Template changes do not migrate existing user-edited role records.

The bundle runtime entry ID is `thaliris`. Custom deployments may choose another ID; find its namespace in `remote.settings.describe()`. Since 0.5.0 its Config has four live fields: `policy`, plus the optional `pythonExecutable`, `corePath` and `authorityDirectory`, which are `.volatile()` and take effect live as a manual override. `subagentProvider` and `bridgeTimeoutMs` remain ordinary native plugin configuration. The three paths are optional strings with unchanged names and positions: when omitted, the host uses the runtime manifest recorded by first-run provisioning, then host-detected Python, and provisions on first use (see [First-run setup](#first-run-setup)). The settings page renders while the Thaliris preset is unselected because it is contributed by the top-level `thaliris` row, not by the preset child.

`ctx.configForms.get<{ policy: UserPolicy; pythonExecutable?: string; corePath?: string; authorityDirectory?: string }>('thaliris')` returns the native form. Use `getSnapshot()`, `subscribe()` and `mutate(ops, expectedRevision?)`. The native form serializes writes and supplies the latest Settings revision; a stale fixed revision is refused. Example atomic role edit:

```ts
await form.mutate([
  { op: 'set', path: ['policy', 'roles', '0', 'name'], value: 'My implementer' },
  { op: 'set', path: ['policy', 'roles', '0', 'prompt'], value: editedFullPrompt },
])
```

For deletion/duplication/reordering, write the complete selected `policy.roles` array (with unique IDs for duplicates). Explicit `[]` is legal and persists. Do not unset the roles field to delete all roles: native unset re-inherits the composition templates. Adding a template explicitly stores a copied record; templates are not active hidden roles. No prompt suffix is applied by the runtime. Default schema roles are empty; the installation composition stores initial templates.

Paths and defaults:

| Path | Shape/default |
|---|---|
| `policy.controllerPrompt` | Visible editable Controller guidance string |
| `policy.workspaces` | `[{workspaceId, root, enabled}]`, default `[]`; exact native ID/canonical Git root |
| `policy.roles` | Full `RoleRecord[]`; schema default `[]`; bundle initial templates |
| `role.id/name/description/prompt/enabled` | User-editable identity/display/full prompt; enabled defaults true |
| `role.tools` | Explicit native tool allowlist; schema default `[]`; bundle-created roles start from the curated template grants |
| `role.modelPolicy` | `{mode:'inherit'|'fixed'|'allowed',routes:[{provider,model,reasoningEffort?}]}`; inherit, empty routes |
| `role.memory` | `{read:[providerId],write:[providerId]}`, both empty |
| `role.context` | `{handoff:true,memory:false}` |
| `policy.memory` | `{mode:'disabled',autoAuthorized:false,providers:[],controllerRead:[],controllerWrite:[]}` |
| `pythonExecutable` | Optional absolute override of the Python interpreter; volatile, default: recorded runtime then host detection |
| `corePath` | Optional absolute Core import root (parent of the `thaliris` package); volatile, default: recorded runtime |
| `authorityDirectory` | Optional authority directory; volatile; default `~/.thaliris/<profile>`; must stay outside the workspace and behind no symlink/junction |

Full public types are exported from `@thaliris/dsh-plugin/remote`. Native ConfigForms distinguishes writable Host mode from process-local memory mode on a non-loopback client. Honor that native state; do not label a process-local preference as a persisted grant. The explicit native `remote.settings.update/replace/mutate` API takes namespace, patch/ops and expected revision. Do not add another settings storage/API. `settings/document-updated` and `connection/reset` already refresh ConfigForms.

For model choices, reuse `ctx.remote.session.modelCatalog()` as the native subagent settings controller does. It returns the native `RemoteResult<ModelCatalog>` envelope: store `response.value` only when `response.ok` is true, and treat a failed result as an unavailable catalog. The initial projection has no catalog until this request succeeds. Join stored allowed routes with current native catalog facts; a previously stored route may be unavailable. Thaliris validates exact route metadata/capabilities at launch, does not rank models, create a model registry or modify user preferences. For workspaces, use the existing native `remote.workspace` projection/page and stored native Workspace IDs. Do not generate replacement IDs or create a workspace/session database. For enable/disable/install/remove use the existing native Plugin Manager page; package changes take effect after a DSH restart (the manager reports `restart-required`, see [Native mode and settings page](#native-mode-and-settings-page)). Runtime, API, memory capability and default provider have independent native effects/entries; the two memory components have separate package manifests.

## First-run setup

Setup is entirely host-side and human-only: it is exposed as three Gateway methods and never as model tools. `setupStatus()` is a synchronous status read; `prepareRuntime(signal?)` runs or joins the single-flight provisioning; `recheckRuntime(signal?)` re-reads and re-verifies the configured/recorded runtime without provisioning. They take no caller IDs and never throw; a failure is a status object carrying `code`, `recovery` and a path-redacted `detail`.

`setupStatus()` value (additive schema): `state` (`unconfigured | detecting | provisioning | verifying | ready | failed`), `verified`, `code`, `recovery`, `detail`, `step`, `attempt`, `elapsed_ms`, `progress` (`{step, started_at, elapsed_ms}` or `null`), `configured` (both explicit paths set), `manual_override` (either explicit path set), `authorityDirectory`, `runtime` (`{pythonExecutable, corePath, version, commit, state_schema_version, python, verified_at, source, version_matches_pin}` or `null`), `pin` (`{version, commit, stateSchemaVersion}`), and `workspaceAutoBind` (the last auto-bound `{workspaceId, root, enabled, at}` or `null`). `prepareRuntime`/`recheckRuntime` return that status plus `ok`, `already`, `provisioned` and `elapsed_ms`.

Provisioning algorithm (host service, never the client): detect CPython ≥ 3.11 (explicit config → `THALIRIS_PYTHON` → `$DSH_HOME/dsh-runtimes/*/dependencies/python` → PATH), create `<authority>/runtime-<core>-py<major.minor>` with `venv --without-pip`, fetch the pinned codeload tarball with Node `fetch`, verify `source.sha256` and `package_tree_sha256` from `core.lock.json`, install `src/thaliris` into the venv purelib with dist-info and a console-script shim, verify imports/version/state schema with the venv interpreter, and write `runtime.json` atomically. No pip, build backend or global tool is used. Cold provisioning measured ≈1.6 s; the first bridge call awaits the shared setup flight inside one deadline (`bridgeTimeoutMs`, default 30 s); a ready runtime short-circuits to one import probe per process. A failed setup leaves the plugin loaded and every tool call failing closed with its code. Single-flight is per process plus `<authority>/provision.lock` (stale after 5 minutes; a second process gets `THALIRIS_RUNTIME_PROVISIONING`).

Workspace first-run auto-bind is host-side: when `policy.workspaces` is empty and the current native workspace's persisted root session is Thaliris-selected, the host row persists `{workspaceId, root, enabled: true}` once through the native config editor and reports it in `setupStatus().workspaceAutoBind`; a non-empty list is never appended to and an unselected session never binds. `diagnostics` additionally reports `workspace.autoBound` on the call that performed the bind.

## Native mode and settings page

The settings page remains a global `plugins.item` contributed by the top-level `thaliris` row, so it renders while the preset is unselected; it gates only on the `thaliris` Settings namespace and is absent when that namespace is not served. The mode itself is native: the roster entry (`id: 'thaliris'`, name `Thaliris`, order 10), per-session selection and the new-task default are owned by DSH's `agent-presets` Settings section and the session composer.

The page has five tabs (`general`, `roles`, `memory`, `context`, `diagnostics`). The General tab adds three onboarding sections before the Controller guidance:

- **First-run setup** (`SetupController` + `setupStatus`): state, whether this process verified the runtime, pinned Core, detected Python/Core versions, authority directory, current step, attempt, elapsed time, failure code/recovery/detail and the three optional overrides. "Prepare Thaliris runtime" calls `prepareRuntime()`, "Re-check runtime" calls `recheckRuntime()`, and "Refresh setup status" re-reads the synchronous status; nothing runs on mount. While an action runs the page polls the status every 800 ms so the active step renders, and the action's response is authoritative. Overrides are edited on the same headerless draft as `policy` and saved by the existing Save action in one revision-fenced mutate (a cleared field becomes an `unset`); validation accepts absolute Windows/UNC/POSIX paths only and applies to edited fields, so a legacy non-absolute stored value cannot block an unrelated save.
- **Agent Preset and new-Session default** (`ModeController`): reads `remote.agentPresets.list()` (tolerating a not-yet-mounted namespace and `gateway/invocation-unavailable`) and the native `agent-preset-registry` ConfigForm (`default`, `selectedDefault`, `revision`, `writable`), and subscribes to the form plus `settings/document-updated`. It renders preset health (healthy / registered but broken / missing / registry unavailable), the native default, the saved override and the effective default, and detects a dangling default (a configured default id that resolves to no roster row). "Set Thaliris as new-Session default" is offered only for a healthy, registered, writable, non-default preset and makes the native call `remote.settings.update('agent-preset-registry', { selectedDefault: 'thaliris' }, revision)`; "Restore native default" makes the same call with the `default` id read from the native section, offered only when a saved override differs or the saved default is dangling. A refused revision fence reloads the native value. Nothing is written on load. The dangling-default warning is shown while Thaliris is the default (disabling/removing the bundle then breaks unnamed new Sessions until another default is chosen), with a separate repair hint when the saved default resolves to no registered preset. A default write never recomposes existing sessions.
- **Recommended native permissions**: lists enabled roles whose `tools` is empty, pairs each with the shipped template of the same id, and annotates each recommended tool as present/absent in the live host catalog (informational; dispatch filters unknown names). "Apply recommended permissions" stages the complete `policy.roles` and saves through the normal revision-fenced `settings.mutate` path, only on click; roles with no shipped template get no guessed recommendation. It shares the normal dirty-draft/Save semantics, so other pending policy edits save in the same mutate.

The Context tab keeps Workspace bindings and adds the host-reported auto-bound row marker (`setupStatus().workspaceAutoBind`), plus an explicit "Bind most recent Workspace" action. The shared page is root-scoped and DSH exposes no public current-session/current-workspace read to a client plugin, so that action is a documented composition over native Workspace/Session snapshots (latest Session `updatedAt`, then `createdAt`); it only stages `policy.workspaces` and Save persists. When the reported auto-bound row is not yet in the native draft the page says so rather than creating anything. Roles keeps the existing complete-record editing (including `role.tools`); Memory and Diagnostics are unchanged.

Role permission model: `role.tools` stays a user-owned native allowlist. Seeded templates now carry curated native DSH grants per capability (investigator; implementer/focused-implementer; reviewer/reasoning-specialist read-only; curator), and dispatch drops names the dispatching host does not provide instead of failing child creation. The plugin never rewrites stored roles silently: the recommended-permissions section above is the only place this adapter offers to write grants, it acts only on an explicit click, and declining or editing manually remains valid.

Lifecycle and restart: row ids `thaliris`/`thaliris-api`, the `thaliris` namespace, preset id `thaliris` and every config field name stay stable from 0.4.x to 0.5.0, so existing profile rows keep loading. User configuration lives in the profile's `cordis.patch.yml`, and task state lives under `authorityDirectory` outside the workspace; upgrade, disable and re-enable do not delete either. Installing, upgrading, disabling or removing the package is a host-process change: restart DSH to make it effective (the native manager returns `restart-required`, possibly with reason `unmanaged-plugin` because the preset is registered at runtime). While the plugin is disabled or removed, sessions that recorded preset id `thaliris` cannot resume (`agent-preset/not-found`); re-enabling and restarting restores them. The page must warn before an action would leave the saved default pointing at the disabled/removed preset.

## Implemented Remote projection

Mount the optional Host plugin `@thaliris/dsh-plugin/api` beside the active runtime. It registers native service `thalirisController`, namespace `thaliris`. The client imports the contribution and mounts through the existing Gateway:

```ts
import { remoteContribution } from '@thaliris/dsh-plugin/remote'
ctx.effect(() => ctx.remote.$mount(remoteContribution))
ctx.inject(['remote.thaliris'], ctx => {
  // Consume the traced namespace from this dependent fiber.
  // Promise<RemoteResult<T>>: inspect response.ok before reading response.value.
  void ctx.remote.thaliris.diagnostics(selectedNativeSessionId)
})
```

The mounting fiber requires `remote`; its dependent page fiber requires `remote.thaliris`. The Gateway creates this namespace as a traced Cordis service, so calling it from a fiber without that injection is rejected even after mounting succeeds. Keeping the dependency on the child avoids a circular startup dependency. The page's initial catalog refresh runs in the dependent fiber, and unload removes both its subscriptions/page and the owned contribution. The Plugins item is named `Thaliris`; `General` labels only its internal tab.

The contribution uses native strict input codecs and the Host's SRC Remote method markers; native Gateway/client mount and dispatch are exercised in the runtime tests. No separate RPC carrier is needed. Inputs contain only native IDs; runtime verifies the exact persisted root ancestry, configured Workspace and Core anchor before resuming a nonresident Session through the native Agent service. Diagnostics and approval dispose only a temporary Agent handle they opened; resident root Agents remain under their existing owner. Signal is the optional final client parameter and is supplied by the native Gateway to the Host method.

| Method | Arguments | Successful value |
|---|---|---|
| `templates()` | none | Detached initial editable role templates; does not change stored roles |
| `providers()` | none | Current registered `[{id,name}]`; empty when capability/providers absent |
| `toolCatalog()` | none | Current native tool registry `[{name,description}]` |
| `diagnostics(sessionId, taskId, signal?)` | Native root Session ID and explicit Core Task ID returned by `thaliris_task_start` | `{task:{state,contract},workspace:{root,workspaceId},configurationRevision:number|null,permissions:{memory,roles},providers,reservations:[{reservation,native}]}` |
| `approveMemory(sessionId, taskId, proposalId, signal?)` | Native root Session, explicit Core Task ID, and proposal ID | Provider write result and Core acknowledgement; consumes the pending proposal and records the native-client approval receipt as a `dsh-memory-approval` record under current grants |
| `setupStatus()` | none | Host-only setup status object (see [First-run setup](#first-run-setup)); never throws |
| `prepareRuntime(signal?)` | optional native Gateway signal | Setup status plus `{ok, already, provisioned, elapsed_ms}`; provisions or joins the single flight, cancellable |
| `recheckRuntime(signal?)` | optional native Gateway signal | Setup status after re-reading and re-verifying the configured/recorded runtime; does not provision |

Diagnostics uses current Core state/intent, native catalog/terminal Session evidence and live Settings. `configurationRevision:null` means native Settings is absent/unavailable; it is not revision zero. Resident child evidence may remain UNKNOWN. Re-query on native task/session activity or an explicit user refresh; never infer Completed from a missing card or catalog activity. No mutable diagnostic state is stored.

Active Work and Pending Results hold only current routing state: the active reservation and unapproved memory proposals. History lives in append-only Core records whose producer `dsh:adapter` and revision the bridge supplies: `dsh-dispatch` (one per finished dispatch: the released reservation and its terminal finish/reconcile observation), `dsh-memory-approval` (`{receipt, proposal}`) and `dsh-legacy-pending` (history an earlier adapter version kept in Pending Results, moved there unchanged on the task's next adapter write; unrecognized entries stay in Pending Results). The Controller's close decision is a `dsh-close-decision` record with producer `dsh:controller`. If Core's record-count or state-size bound refuses an adapter record, the release or close still applies and its result returns the text as `unrecorded` with `unrecorded_reason`.

Unapproved memory proposals are JSON entries in `task.state.pending_results`, distinguished by `proposal_id`. Their policy, provider, key, text, provenance, selected role and Workspace ID are retained. Native-client approval receipts carry `approval_id` and the same proposal ID; they are read from `dsh-memory-approval` records (and, for not yet migrated tasks, from Pending Results). The Diagnostics view renders proposal content once and displays receipts as approval evidence; receipts do not become proposal cards. A view may show these records and an explicit user review action; it must not auto-approve proposals, treat Curator text as approval, or enable auto policy on its own. Auto requires explicit persisted user opt-in. Provider response limits apply to serialized UTF-8 bytes. Provider writes may be completed before a subsequent Core receipt failure; report that outcome as uncertain and refresh evidence/provider state rather than fabricate failure or success. Providers own write idempotency.

## Tool/runtime contract

The Controller's native tool calls are independent of UI:

- `thaliris_task_start({goal,contract})` selects actual human intent and execution mode.
- `thaliris_task_inspect({task_id})` reads only the explicitly selected Core task and contract. A native root Session may have multiple independent Core tasks; never infer a current task from its Workspace or another task's ACTIVE state.
- `thaliris_workstream({task_id,base_revision,workstream,role,handoff,route?,memoryContext?,evidence?})` takes an enabled role ID. The role is snapshotted at dispatch: its prompt, tools and memory grants govern that child for its whole run, and the reservation records `role_sha256` and the chosen `route` (`'inherit'` or `{provider,model,reasoningEffort?}`). `evidence:{candidate,requirement_refs}` registers a Core handoff atomically with the reservation (requirement refs must already be registered) and grants that child `thaliris_observe` until the dispatch ends. The result carries `route`, `role_sha256`, any `evidence_handoff_id`/`candidate`, the new `revision`, and `evidence_continuity`: the compact open-evidence summary the release returned (totals plus bounded items, `next_offset` pages the rest; `UNKNOWN` if absent). `handoff` has goal/scope/invariants/acceptance/context strings. Allowed model mode requires the supplied route; inherit forbids an override. `memoryContext` is at most four explicit selections `{provider,operation:'read'|'search',key? ,query?,limit?,maxBytes}`; bytes 1–16384 and search limit 1–20. Results reach only that selected handoff and require Controller plus selected role grants/context permission. No ambient memory is injected.
- `thaliris_reconcile({task_id,base_revision,action:'check'|'reconcile'|'cancel-reconcile'|'dispose',reason?})` reads exact native correlation/terminal evidence. Check never releases. Reconcile only releases proven terminal work and preserves reservation/evidence in a `dsh-dispatch` record. Cancel-reconcile handles an exact resident native child first. A missing child Session file or working directory is UNKNOWN with a reason. UNKNOWN remains reserved until the Controller decides `dispose` (requires `reason`, accepted only there): a child of this reservation resident under this root is cancelled first (one resident under another root is refused), and the `dsh-dispatch` record has `operation: 'dispose'` and result `{outcome:'disposed', native_outcome:'UNKNOWN', child_liveness, reason, provenance:'controller-dispose'}`, never completed. Evidence, records and other task state stay.
- `thaliris_task_recover({action:'list'|'rollback'|'attach'|'attach-and-rollback',task_id?,expected_authority_sha256?,reason?})` is Controller-only and never automatic. `list` returns this root's `recovery_required` tasks and this Workspace's `attachable` tasks of other roots (id, digest, `state_changed`), plus the resume counts. `rollback` answers `TASK_AUTHORITY_STATE_CHANGED`: Core `AuthorityStore.recover` checks the anchor digest, archives the current ledger and anchor bytes under the authority directory and restores the last anchored ledger; it is refused while the ledger still matches its anchor or when protected configuration changed. `attach` moves the single Controller anchor (`dsh_controller_id`) of an ACTIVE task of the same Workspace to this root; Task ID, goal, contract, mode, ledger and evidence stay, the previous root is refused afterwards, and a changed ledger needs `attach-and-rollback`. Every change needs `expected_authority_sha256` (from `list` or the error `details.authority_sha256`) and a `reason`. Errors: `TASK_AUTHORITY_STATE_CHANGED` and `DSH_CONTROLLER_MISMATCH_OR_INACTIVE` keep their text and, for this root or Workspace, add `code`, `recovery` and `details`.
- `thaliris_task_status({task_id,evidence_offset?,view?,since_revision?})` is compact by default (`view: "compact"`): Core's compact packet (`Task` with `revision`, `Active Work`, `Pending Results`, `Counts`, and `Evidence`: unincorporated/unresolved totals plus bounded open items, paged by `evidence_offset`), `Current Records` (up to twelve non-superseded Controller-facing records as `{id,kind,text}` with the text clipped to 200 characters and an ellipsis; adapter history records excluded) with `Current Record Count`, `Dispatch History` (`count`, `legacy_count` and up to four recent `non_completed` dispatches), and the authority `status`/`execution_mode`/`sha256`. `view: "full"` returns the previous packet (`Evidence Continuity` with `unincorporated`, `unresolved_judgments` and `latest_judgments`, 600-character records with `status`/`revision`, the eight most recent `Dispatch History` summaries) and keeps the bounded task-context summary in the result. `since_revision` adds Core's bounded `Changes Since` review hint (not an exact delta). The task-context summary is not echoed in other tool results: it is re-supplied as dynamic context.
- `thaliris_task_context({task_id,base_revision,records?,sources?,milestone?})` appends Controller records `{id,kind,text,source_refs?,status?,supersedes?}` and sources and sets the milestone (`""` clears it). The result carries the new `revision`, `Task Context` (milestone, `Current Record Count`, current record ids and kinds) and the compact `evidence` summary. The bridge supplies record producer `dsh:controller` and revision; reservations and pending results are not editable here. The bounded summary is re-supplied to that native root as DSH dynamic context (`thaliris:task-context`); after a process restart it is restored from ACTIVE tasks whose authority anchor names that exact root Session and Workspace, and that root's first prompt assembly awaits the restoration.
- `thaliris_task_register({task_id,base_revision,requirements:[{id,workchain_ref}]})` appends opaque requirements; the result carries the new `revision`, `appended` and the compact `evidence` summary. Handoffs are never Controller input; they are registered only by `thaliris_workstream`.
- `thaliris_task_judge({task_id,base_revision,judgment:{id,candidate,requirement_ref,observation_refs,outcome,reasoning,judgment_refs?}})` appends a Controller judgment; Core assigns `task_id` and producer and validates references. `outcome` is `satisfied`, `unknown`, `repair` or `no-current-impact`. Instead of `judgment`, `judgments: [...]` (1-64, exactly one of the two) appends an ordered batch atomically under one revision: any invalid item (the error names `details.collection`, `index` and field) leaves the ledger unchanged. The result carries the new `revision`, `appended` ids and the compact `evidence` summary (open items are re-presented, paged by `next_offset`, never dropped).
- Revision conflicts: every revision-checked tool (and `thaliris_reconcile`) fails with the historical text `TASK_ID_OR_REVISION_CONFLICT` followed by a JSON envelope `{code, recovery, details}` (also exposed as `error.code`/`recovery`/`details`). `code` is `TASK_REVISION_CONFLICT` (or `TASK_IDENTITY_CONFLICT`); `details` has `mismatch` (`revision` or `task_id`), `task_id`, `base_revision`, `current_revision` and `changes_since` (a bounded, non-exact review hint with recent handoffs, observations and judgments, and the open-evidence summary). Nothing is rebased or merged: the hint is approximate (`exact: false`; `recent` is the last min(revision gap, 16) items per collection and can omit items one batch wrote in a single revision; replaced fields such as Active Work, Pending Results, milestone and status, and sources, are not tracked). After review, if the write still applies, retry it once with `base_revision = details.current_revision`; read compact status when you need Active Work/Pending Results or anything the hint does not cover. Other Core failures that carry a `code` (for example `CONTINUITY_REFERENCE_INVALID`) surface the same way.
- `thaliris_task_mode({task_id,base_revision,expected_authority_sha256,mode,human_instruction})` calls Core `AuthorityStore.switch_mode` under authority-digest and revision CAS. It is refused while a reservation is active. Only `execution_mode` changes; `thaliris_workstream` requires `delegated`.
- `thaliris_task_identity({task_id,action:'status'|'get'|'trace',version?,items?,amendment?,challenge?,ref?,direction?,depth?})` reads Core's Project Identity for the explicitly selected, authority-checked task; it does not need `base_revision`. `status` returns the state (`ABSENT`, `CURRENT`, `UNRECORDED_CHANGE` or `INVALID`), item ids, open challenges and the summary line, and refreshes the cached task context. `get` takes one of: nothing (the recorded current version), `version`, `items` (item ids), `amendment` (`A-000N`) or `challenge` (id). `trace` takes `ref` and optional `direction` (`up`|`down`|`both`) and `depth` (1-4). Parameters foreign to the action are refused. Bridge operations: `identity_status`, `identity_get`, `identity_trace`.
- `thaliris_task_identity_amend({task_id,base_revision,base_version,base_sha256?,text,summary,rationale,decision:{decided_by,human_instruction},challenge_text?,why_not_lower?,evidence_refs?,resolves?,affected_refs?})` records an amendment (`base_version: 0` establishes v1) under task-revision CAS. `base_sha256` is `on_disk_sha256` from status and is omitted when no `IDENTITY.md` exists (the bridge sends null). `decision.human_instruction` is the quoted explicit decision of the human owner; Core cannot verify a human, so it is Controller-asserted like Task Authority. The result carries Core's item diff, registered dependents (registered relations only; nothing is revalidated or propagated automatically) and resolved challenges.
- `thaliris_task_identity_challenge({task_id,base_revision,targets?,summary?,text?,evidence_refs?,proposed_change?,dismiss?,reason?})` opens a challenge (`targets`, `summary`, `text`) or dismisses an open one (`dismiss`, `reason`); Core refuses any other combination. Only an amendment's `resolves` marks a challenge `amended`.
- `thaliris_task_identity_relate({task_id,base_revision,add?:[{from,rel,to,note?}],retract?:[{id,reason}]})` registers or retracts purpose relations; `rel` is `serves`, `supports`, `challenges` or `supersedes`, and a `challenges` relation may not target identity (use a challenge).

- `thaliris_task_identity_note({action:'add'|'retract'|'list',quote?,kind?,context?,refs?,retract?,reason?,include_retracted?})` (Core 0.5.2) records one basis note of the user's verbatim words (`add`: `quote`, optional `kind` of `purpose`, `direction`, `constraint`, `non-goal`, `decision`, `rejection`, `material` or `other`, one-line `context`, up to 16 `refs`), withdraws one (`retract` note id, `reason`) or lists notes with their `pending` flag. Notes live in Core's machine-local store under `THALIRIS_HOME` (default `~/.thaliris`), not in the repository, and need no `task_id`, no ACTIVE task and no `base_revision`. Bridge operations: `identity_note`, `identity_note_list`.
- `thaliris_task_identity_suggest({scope:'session'|'workspace'|'project'|'global',setting:'on'|'off'|'clear'})` sets or clears the preference for proactive identity offers only on the user's words; it needs no ACTIVE task. The session scope is keyed by the native Controller session id the bridge already carries (`native_controller_id`). `thaliris_task_identity` `status` additionally returns `basis` and `suggestions`. Bridge operation: `identity_suggest`.
- A successful `thaliris_task_close` result carries an `identity_offer` line only when Core returns one (suggestions enabled, identity ABSENT or CURRENT, and a note newer than the last one offered); it is never injected at session start or into the dynamic task context, and a failure leaves the field absent.

The six identity tools are Controller-only: they are registered without child access, begin with `thaliris_task_` (so a role grant can never include them) and are on the dispatch deny list. The two formation tools run without task authority (the plugin still requires the native root Controller; the bridge selects no task for them, so Core records `task_id: null` on their notes). The bridge takes the actor (`dsh:<native controller id>`) from the native Controller identity, never from arguments, and rebuilds the task context from the result because the identity line may have changed. Identity writes neither bump the task revision nor touch the task ledger or the Memory Provider. Inputs are bounded by the 64 KiB tool-argument limit, so an amendment's text plus its other fields must fit in it.
- `thaliris_observe({id,text,source_refs,sources?,observed_state?})` is child-only and exists only for a dispatch with an evidence association. The bridge requires the active reservation to be bound to that exact native child and handoff, namespaces child IDs as `<handoff>.<id>`, and takes producer (`handoff:<id>`), candidate and requirement refs from the registered handoff; `native_actor` is a hash of the child ID. A finished dispatch, a root caller, or any provenance field in the payload is refused.
- `thaliris_task_close({task_id,base_revision,decision})` mechanically records task `DONE` after Core's task-state/revision checks and optional expected-ID check. It does not evaluate a verification target or determine product completion; Controller judges that against the original objective and criteria using available evidence before requesting close.

Task IDs returned by start select Core state, authority, reservation, proposal and approval records for each subsequent call. Starting a new task in the same Workspace creates an independent ledger and authority anchor even when an older task remains ACTIVE/UNKNOWN or has an unresolved reservation. Such old-task observations do not block a different Task ID. A missing or damaged selected task authority remains an error for that task and does not select another task. The `task_id` field is required for `thaliris_memory_propose`; every write validates the selected task and its current Authority before appending a proposal or invoking a provider. Child writes must also match the exact Task ID granted to that child. Read/search remain explicit provider calls and do not need a Core task selection. Memory proposals and approval records are written to the selected task without migration from another task.

The Diagnostics page requires both the native root Session and the explicit Task ID. It does not auto-select a Workspace task or silently reuse an earlier Task ID when the selected Session changes. With no Core task catalog in DSH, users can supply the ID returned by `thaliris_task_start`.

Optional memory tools read/search under explicit byte/item bounds and propose writes. Children need native tool allowlist membership and current enabled role grants/context permission. The model-facing tools expose no policy mutation or approval endpoint. Tasks/close/routing remain usable after memory capability removal.

## Client behavior and packaging

The shared client registers in native `plugins.item` only while the Host serves `thaliris`. General carries the first-run setup panel, the Agent Preset/new-Session default panel, the recommended-permissions panel and `policy.controllerPrompt`; Roles edits complete records, supports custom and empty role sets, explicit templates, duplication with a new unique ID, deletion, exact native routes, native tool grants, and role memory/context permissions; Memory exposes write mode, independent auto-write consent, provider enablement and Controller grants, with each role's controls labeled by its name and ID; Context binds native Workspace IDs (showing the host-reported auto-bound marker and role context permissions); Diagnostics reads a selected native root Session, displays Core and native observations, opens a correlated child Session, copies a valid reconcile request, and exposes an explicit proposal-approval action only when current grants permit it. A Settings revision conflict exposes the page's explicit reload action, which discards the local draft and reads the latest native values. Approval remains disabled while a request is pending; failures display the returned detail with the provider-write uncertainty guidance.

The component uses native locale and settings primitives. Editable data remains on the `thaliris` ConfigForm with revision-fenced atomic mutations. The only client-side policy state is the unsaved page draft. Duplicating a role copies its visible fields and grants while assigning a new unique, stable ID. Diagnostics, Workspace, Session, model, provider, and tool values are native projections; they do not become a second Settings, Session, Workspace, or task store. Desktop uses the same DSH Web client registration and module bundle.

`dsh.client` declares the shared client dependencies, and `./client` resolves to the generated DSH closure-factory artifact in `lib/client.js`. Build from the pinned DSH source with `npm run build:client` and `DSH_SOURCE` set; component tests use `npm run test:client`. The activation smoke takes `THALIRIS_PACK_DIR`, `DSH_SOURCE`, `THALIRIS_TEST_TMP_ROOT`, `THALIRIS_TEST_PYTHON`, and `THALIRIS_TEST_CORE_PATH`. It installs the real local archives through the native Plugin Manager in an isolated profile, then resolves and activates their packed runtime, API, memory capability, and provider entries through the native Host Loader. A Core wheel is installed in the fresh test environment; the smoke starts, inspects and explicitly closes a task through the packed runtime and local subprocess, removes the optional memory packages, then confirms the task can still be inspected and closed. The two optional memory packages ship their own disabled-by-default bundle patches and are independently removable through the existing native Plugin Manager.

Client tests (20, jsdom with the real client module stack) cover native Settings revision conflicts, role create/edit/duplicate/delete/empty persistence, model and tool selection, Workspace binding, separate memory consent and grants, absent providers, native diagnostic projections, explicit proposal approval, and actual slot/Gateway contribution mount and disposal.
